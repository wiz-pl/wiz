# Datalog store/index benchmark

This is the committed source of the Datalog speed claim that used to live only in
`wiz-notes/scry-datalog.md` §8.3 (the "~160–210×" line). It pins the two revisions,
the fixed inputs and queries, the driver, and the measured JSON/TSV. There are no
numbers in the documentation without a matching artifact here.

## What is compared

Both engines are **semi-naive**; the change is the store, not the delta loop:

| | revision | `Scry.Store` / `Scry.Eval` |
|---|---|---|
| old | `bb1a6294` | authoritative row lists; dedup is a scan, joins are full scans |
| new | `1fde883a` | hashed dedup plus `(column, value)` join indexes, indexed provenance; same delta loop and rules |

`1fde883a` is the commit that landed the change. `lib/Scry/Store.wiz` and
`lib/Scry/Eval.wiz` are identical in `1fde883a` and `master` at the time of this
measurement (`git diff 1fde883a master -- lib/Scry/Store.wiz lib/Scry/Eval.wiz` is
empty), so the "new" column describes the current engine as well.

The harness also has a third program, `naive`: one round of every rule against the
whole store, repeated to the fixpoint, using the same kernels (`Scry.evalAtoms`,
`Scry.applyMatches`). It is a round-scan baseline, *not* the historical "old" engine
(the old engine was already semi-naive). The authoritative earlier claim is the
old/new comparison; the naive rows are a separate, smaller experiment.

## Inputs and query set

`queries.json` pins the programs and the deterministic derived counts the driver
checks before timing. The inputs are generated by `examples/scry-datalog-bench.wiz`
from a fixed size; the driver runs the harness's `dump` command and hashes the EDB
rows, so a generator change is caught even though no input file is checked in.

| case | EDB rows | input sha256 (first 16) |
|---|---:|---|
| `chain 1000` | 2 001 | `b25d0694e4325835` |
| `chain 5000` | 10 001 | `6af6e182a8742a49` |
| `tc 20` | 1 281 | `13dd570a2800cf8c` |

`chain N` is the taint-shaped program: `flow(i,i+1)`, `src(0)`, `sink(i,0)`, no
sanitiser, so it derives `N+1` `tainted` and `N-1` `alert` facts with joins on bound
columns. `tc N` is the 8-wide layered transitive closure: 64N edges from the 8×8
blocks plus one final spine edge; the other N−1 spine edges duplicate the block's
`(0,0)` edge, so the EDB has 64N+1 unique rows.

## Reproduce

```sh
python3 scry/bench/datalog/run.py            # 3 interleaved rounds, rewrites results.json/tsv
python3 scry/bench/datalog/run.py --check    # rebuild + verify the pinned hashes only
```

The driver creates throwaway `git worktree`s at the two revisions under `/tmp`, copies
the harness, builds both with `wiz build`, warms each engine once per case, then measures
3 rounds. It never modifies the checkout. Requirements: `wiz` on `PATH`, `git`, and a
`wiz build` that can compile and link C (the installed toolchain supplies GMP and GC;
this is what produced the numbers below).

## Measured result (2026-11-17)

- host: AMD Ryzen AI Max+ 395, 32 threads, Linux 7.3.3
- toolchain: `wiz 0.1.0-dev (aeaa34ef8527c2a72e703959742f7a99d9c03fc9)`
- load average 1-min during timed rounds: 17.0, 16.5, 19.1 (5-min 23.1→21.0);
  end 22.8. This is a **shared machine** measurement, informational, not a
  `perf-run` measurement.
- 3 interleaved rounds; medians below. `eval` is the harness's own `eval_ms`;
  wall includes process start and EDB build.

| case | old eval | new eval | speedup | old peak RSS | new peak RSS | old wall | new wall |
|---|---:|---:|---:|---:|---:|---:|---:|
| `chain 1000` | 220 ms | 9 ms | **24.4×** | 15.5 MiB | 15.5 MiB | 238 ms | 18 ms |
| `chain 5000` | 5 680 ms | 49 ms | **115.9×** | 15.5 MiB | 19.2 MiB | 6 005 ms | 88 ms |
| `tc 20` | 71 822 ms | 401 ms | **179.1×** | 17.2 MiB | 16.5 MiB | 71 846 ms | 430 ms |

Two further 3-round runs (load 23–31 and 21–55) gave `chain 1000` 26.4×/26.6×
(238→9 ms, 239→9 ms), `chain 5000` 102.1×/119.7× (5 922→58 ms, 5 867→49 ms) and
`tc 20` 187.4×/215.4× (66 884→357 ms, 69 791→324 ms). The spread is machine load,
not a different result: the load-independent statement is **about 100–120×** on
`chain 5000` and **about 180–215×** on `tc 20`. The old "~200×" is therefore an
upper-end figure for `tc 20`, not a single number for the change; `chain 5000` is
about half that on this machine. The new engine uses more memory on `chain 5000`
because the join indexes grow with rows × arity (15.5 → 19.2 MiB).

Per-round values and all counts are in `results.json` and `results.tsv`.

### Naive round-scan baseline

The naive evaluator re-runs every rule against the full store each round. On the same
3 rounds:

| case | naive eval | semi-naive eval | naive / semi-naive | naive peak RSS |
|---|---:|---:|---:|---:|
| `naive chain 1000` | 3 161 ms | 9 ms | 351× slower | 15.5 MiB |
| `naive tc 20` | 4 677 ms | 401 ms | 11.7× slower | 58.1 MiB |

The delta loop is worth ~351× on the linear `chain` shape (it derives one layer per
round and does no re-derivation), but only ~12× on the dense `tc` closure, where most
of the work is re-confirming facts that are already known. This is a separate
measurement; it is not the old/new comparison and is not the source of the historical
claim.

## Staleness guard

`results.json` records the harness sha256, each input's EDB sha256 and row count, both
revisions, the toolchain, the load averages and the per-round records. `--check`
rebuilds the new revision and fails if the harness or an input hash moved:

```sh
$ python3 scry/bench/datalog/run.py --check
ok: harness and 3 input hashes match scry/bench/datalog/results.json
```

Changing a rule, a generator or a program size therefore requires re-running the
benchmark and updating this README's table with the new `results.json`; it cannot
silently leave an old speedup in the docs.

## CI handover

`ci.yml` is owned elsewhere and no `scry.yml` exists on `master` yet. When it does, the
one-line step is:

```yaml
- run: python3 scry/bench/datalog/run.py --check
```

It builds only the new revision, takes a few seconds, and needs `wiz` on `PATH`; it
does not run the 3-round measurement.
