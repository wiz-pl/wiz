## What the controls revealed

| control check | count |
|---|---:|
| fixed controls run | 16 (14 in scope, 2 out of scope) |
| controls with a rule finding (false positive) | 0 (0 in scope) |
| controls with memory diagnostics only | 10 (10 in scope) |
| controls with zero findings and zero memory diagnostics | 6 (4 in scope) |
| controls with lowering-boundary warnings | 16 (14 in scope) |

All in-scope fixed controls produced zero **rule** findings. That is the precision side of the 2x2: the controls did not trigger the rule families. It does not mean the analysis proved them safe; see the boundary and memory columns below.

A fixed control with `memory > 0` is **not** counted as a rule false positive, but it is not a strict clean negative either: the analysis reached a pointer whose target it could not bound. A control with `boundary > 0` has a lowering boundary, so its zero finding count is unproven rather than a verified TN.

**Every fixed control has at least one lowering boundary.** The zero rule-finding count is therefore a zero-alert observation on a partially lowered program, not a proof that the analysis understood the fix. This is the main result of the control side of the corpus: the controls expose how much of each fixed shape is outside the frontend, even when no rule fires.

## Confidence caveats

* **n is small and hand-picked.** 14 in-scope pairs (14 vulnerable cases and 14 in-scope fixed controls), 8 out-of-scope pairs. The corpus is selected for small, buildable reductions, not sampled at random from the CVE population. The Wilson intervals above are the only statistical statement; with this n they are wide.
* **Case level, not finding level.** Each vulnerable case has one expected finding in this slice, so the 2x2 is not a multi-sink recall measure. `matched`/`expected` and the finding-level precision are reported separately.
* **The controls are not independent safe code.** A fixed control is the vulnerable file with the known fix applied, so it tests the rule's behaviour on that fix, not general precision on unseen safe programs. Precision here is a fixed-control proxy; it is not a TPR/FPR claim about real code.
* **Memory diagnostics are not bug claims.** `unknown-memory` and `unknown-indirect` mean the analysis could not bound a pointer. They are excluded from the rule-FP count and reported separately. A fixed control with memory-only diagnostics is a coverage boundary, not a verified true negative.
* **Lowering boundaries weaken a zero.** A fixed control with `boundary > 0` may be clean because the relevant construct was havoc'd. The boundary column is the guard against reading such a zero as proof.
* **The reductions are not the full upstream programs.** They keep the vulnerable function and its data flow and replace network/file plumbing with `read(2)`. A full build of OpenSMTPD, Exim, Samba, the Linux kernel, Apache or OpenSSL is out of scope.
* **Out-of-scope entries are explicit.** 8 pairs have no rule family in this tool version; they are listed with reasons and excluded from the 2x2. The CWE-476 probes are the sharpest case: the S5 nullness alarm exists in `lib/Scry/AiFixpoint.wiz` but is not wired into `scry taint`, so there is no null-deref sink.
* **Timing is informational** on the shared machine (AGENTS.md); this driver is not a `perf-run` measurement. Per-case wall time and peak RSS are `wait4`/`ru_maxrss` for one child.
* **No tuning.** This corpus is measurement infrastructure. No rule or analysis was changed to make a case pass.

## Reproduce

```sh
cd scry
cp ../grail.local.wiz .                      # once, if absent
../.lake/build/bin/grail build scry
scripts/cve-bench-v2.sh --timeout 120 --max-nodes 200000 --write-report
diff build/cve-v2/report.md bench/corpus-v2/report.md
```

Regenerate-and-diff is the audit: the 2x2, per-pair and out-of-scope
tables must match the checked-in file. Only the provenance rows (date,
wall time, run wrapper) and the per-case `ms`/RSS columns are expected
to differ, because timing is informational on a shared machine.

The corpus is pinned by `bench/corpus-v2/corpus.sha256`; check it with
`scripts/check-cve-report.sh`. That check also compares
the recall quoted in `README.md` with the recall in this report, so a
stale number fails visibly instead of drifting.

`--case <id|pair|cve>` runs one case/pair; `--no-run` only summarises existing `build/cve-v2` output; `--write-report` also writes this report to `build/cve-v2/report.md`; copy it to `bench/corpus-v2/report.md` after the diff. `CC=...` overrides the compiler. The v1 driver (`scripts/cve-bench.sh`) and its twelve cases are unchanged.
