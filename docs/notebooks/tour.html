1: values and functions

Definitions are values. The #eval lines print the values in the comments; #check @compose prints the type with its implicit arguments.

In [2]:
import Prelude

def answer : Nat := 42
#eval answer                                   -- 42

def double (n : Nat) : Nat := n + n
#eval double 21                                -- 42

-- a function is a value; `fun` makes one
def twice (f : Nat → Nat) (x : Nat) : Nat := f (f x)
#eval twice (fun n => n * 3) 2                 -- 18

-- implicit arguments, in braces, are found by unification
def compose {A B C : Type} (g : B → C) (f : A → B) : A → C := fun x => g (f x)
#eval compose double double 5                  -- 20
#check @compose
42
42
18
20
compose : {A : Type} → {B : Type} → {C : Type} → (B → C) → (A → B) → A → C

Functions are curried, and application is juxtaposition: twice f x. Arguments in parentheses are explicit. Arguments in braces are implicit: you don't write them, and the elaborator works them out from the others (here A, B and C from the types of g and f). #eval e evaluates e and prints its value; #check e prints its type, and #check @compose shows the implicit arguments too:

Types are values like any other, of type Type, which is why A can be an argument. The Prelude has the usual types: Nat (arbitrary precision), Bool, String, List, Option, pairs A × B. It also has let, if … then … else, ++ and list literals:

let, if, ++ and list literals; values print as terms.

2: inductive types and pattern matching

An inductive type and a function by cases. The #eval prints the area.

In [4]:
inductive Shape where
  | circle (r : Nat)
  | rect (w h : Nat)

-- `.circle` is `Shape.circle`: the type is known from the expected type
def area : Shape → Nat
  | .circle r => 3 * r * r
  | .rect w h => w * h
#eval area (.rect 3 4)                         -- 12
12

An inductive type lists its constructors, which live in its namespace: Shape.circle, Shape.rect. Where the expected type is known you can write just .circle. A function can be defined by cases directly, as area is, or with match e with | … => …. Types take parameters, and recursion is fine as long as it is on a smaller piece of the argument (it is structural, so the checker knows it stops):

A recursive, parameterised type; Tree.toList walks it.

In [5]:
inductive Tree (A : Type) where
  | leaf
  | node (l : Tree A) (x : A) (r : Tree A)

def Tree.toList {A : Type} : Tree A → List A
  | .leaf => []
  | .node l x r => Tree.toList l ++ [x] ++ Tree.toList r

def t : Tree Nat := .node (.node .leaf 1 .leaf) 2 (.node .leaf 3 .leaf)
#eval Tree.toList t                            -- .cons 1 (.cons 2 (.cons 3 .nil))
.cons 1 (.cons 2 (.cons 3 .nil))

Matching works on several values at once, with _ for "anything", and patterns nest:

Patterns on two lists at once, with _ for anything.

In [6]:
def zipWith {A B C : Type} (f : A → B → C) : List A → List B → List C
  | .cons a as, .cons b bs => .cons (f a b) (zipWith f as bs)
  | _, _ => .nil

A match must cover every case: leave one out and wiz check says which ("missing case for constructor …"). Under the hood an inductive type is a description, a value that says what its constructors look like, and its least fixed point. That is how the kernel can stay small; stages/04-data.md tells the story. (examples/tour/02-data.wiz.)

3: structures

A record: its constructor, projections, named arguments, an update and a pattern.

In [7]:
import Deriving

structure Point where
  x : Nat
  y : Nat
  deriving Repr

def origin : Point := ⟨0, 0⟩                -- `Point.mk 0 0`, from the expected type
def p : Point := Point.mk (y := 4) (x := 3)  -- named arguments, in any order
#eval p.x + p.y                              -- 7

-- update a copy, and take a structure apart with a pattern
def shiftRight (q : Point) : Point := { q with x := q.x + 1 }
#eval Repr.repr (shiftRight p)               -- "Point.mk 4 4"

def manhattan (q : Point) : Nat :=
  let ⟨a, b⟩ := q
  a + b
#eval manhattan p
7
"Point.mk 4 4"
7

A structure is a record: one constructor (Point.mk) and a projection per field (p.x). The anonymous constructor ⟨…⟩ builds one when the type is known, and also works as a pattern. { q with x := … } is a copy with some fields replaced. deriving Repr writes the instance that turns a point into text (type classes are next). Wiz has no record literal of the form { x := 3, y := 4 }; use the constructor, with named arguments if you like.

A field's type may mention earlier fields. Here the second field is a proof about the first (proofs are section 6):

A field whose type is a proof about an earlier field.

In [8]:
structure Positive where
  n : Nat
  pos : Nat.lt 0 n = .true
def five : Positive := ⟨5, rfl⟩

In the kernel a structure is a Σ type, a dependent pair, so ⟨5, rfl⟩ is a pair whose second component's type depends on the first. (examples/tour/03-structures.wiz; stages/13-language.md, 13a, 13h, 13i.)

4: type classes and numerals

A class and three instances; #eval uses instance resolution.

In [9]:
class Describe (A : Type) where
  describe : A → String

instance : Describe Bool where
  describe := fun b => if b then "yes" else "no"
instance : Describe Nat where
  describe := fun n => Nat.repr n
-- an instance that needs another instance
instance {A : Type} [Describe A] : Describe (List A) where
  describe := fun xs => match xs with
    | .nil => "nothing"
    | .cons x _ => "starts with " ++ Describe.describe x

#eval Describe.describe [Bool.true, Bool.false]   -- "starts with yes"

def shout {A : Type} [Describe A] (a : A) : String := Describe.describe a ++ "!"
#eval shout (7 : Nat)                              -- "7!"
"starts with yes"
"7!"

A class is a structure of operations, and an instance is a value of it. An argument in square brackets, [Describe A], is an instance argument: the caller doesn't pass it, the elaborator finds it by instance resolution, which also chains instances (the one for List A uses the one for A). (7 : Nat) is a type ascription.

Arithmetic is built the same way. a + b is Add.add a b, and a numeral 5 at a type other than Nat is OfNat.ofNat 5, so the same syntax works at every numeric type that has instances:

The same arithmetic syntax at Int and U8, and a function generic over Add and OfNat.

5: dependent types

A type can depend on a value. The classic example is the vector, a list whose type says how long it is:

The tour defines the family inline:

inductive Vec (A : Type) : Nat → Type where
  | nil : Vec A .zero
  | cons {0 n : Nat} (x : A) (xs : Vec A n) : Vec A (.succ n)

-- `head` only takes vectors of length `n + 1` (`.succ n`): there is no `nil` case to write
def Vec.head {A : Type} {0 n : Nat} : Vec A (.succ n) → A
  | .cons x _ => x

-- the types say that `map` keeps the length and `zip` needs two equal ones
def Vec.zip {A B : Type} {0 n : Nat} : Vec A n → Vec B n → Vec (A × B) n
  | .nil, .nil => .nil
  | .cons a as, .cons b bs => .cons (a, b) (Vec.zip as bs)

This notebook imports lib/Vec.wiz instead: section 10 imports Hdl.Core, which imports the same module, so an inline definition would collide with it. head, map and zip keep the length in the type, as the tour explains.

Vec A is a family of types, one for each length. The part after the colon, : Nat → Type, is the index, and each constructor says which member of the family it builds. Vec.head needs no case for nil, because a Vec A (.succ n) cannot be nil: the checker knows, and Vec.head (Vec.nil : Vec Nat 0) is a type error:

(?m0 and ?m1 are the implicit arguments the elaborator was solving for.) In Vec.zip there are no mismatched cases either, because both vectors have length n. In def v : Vec Nat 3 the numeral 3 and the length .succ (.succ (.succ .zero)) that the three cons build are the same number, so the definition checks.

The 0 in {0 n : Nat} is a quantity: the length is only used in types, so it is erased, and at run time a vector is just a list (section 7). Types can also be computed by ordinary functions:

A type computed by a function; the pair and Unit are the two cases.

6: propositions and proofs

Propositions are types, and a proof is a value of that type. a = b is the proposition that a and b are equal, and rfl proves it when both sides compute to the same value:

Propositions are types and rfl proves computation; double is from section 1.

In [13]:
import Logic

def two_plus_two : 2 + 2 = 4 := rfl

def double_three : double 3 = 6 := rfl

A statement about every n is a function from n to a proof, and a proof by induction is a recursive function. zero_add below recurses on n, and the case for .succ n uses the proof for n:

Induction is recursion; #print axioms shows the proof is axiom-free.

In [14]:
def congrSucc {a b : Nat} (e : a = b) : Nat.succ a = Nat.succ b :=
  transp (fun b _ => Nat.succ a = Nat.succ b) (refl (Nat.succ a)) e

def zero_add : (n : Nat) → 0 + n = n
  | .zero => rfl
  | .succ n => congrSucc (zero_add n)
#print axioms zero_add
'zero_add' does not depend on any axioms

transp is the eliminator of equality: from a = b and something that holds at a, it gives the same thing at b. congrSucc uses it to show that equal numbers have equal successors. #print axioms zero_add says the proof does not depend on any axioms.

Chains of relations have their own notation, calc. Adjacent steps compose through an instance of Trans, and the last step's relation is the result:

A calc chain: each step's relation composes with the next.

In [15]:
def lt_of_chain (a b c d : Nat) (h1 : a ≤ b) (h2 : b < c) (h3 : c ≤ d) : a < d :=
  calc a ≤ b := h1
       _ < c := h2
       _ ≤ d := h3
#print axioms lt_of_chain
'lt_of_chain' does not depend on any axioms

_ is the previous step's right endpoint (an explicit middle term must be the same). Trans instances for = and ↔ are in lib/Logic.wiz; Nat, Int and Q register =, ≤ and < (and ≈ at Q) in lib/Nat.wiz, lib/IntOrder.wiz and lib/Rat.wiz, and a program adds its own relation by declaring a Trans instance for it. A chain elaborates to nested Trans.trans applications, so it is checked like any other proof and names no axioms; a step whose proof has the wrong relation, or a pair of relations that no instance composes, is reported at that step. (examples/tour/06b-calc.wiz; stages/13-language.md, 13s.)

Equality in Wiz is observational: a = b is not an inductive type but computes from the type of a and b. At a function type it is pointwise equality, so function extensionality is a definition, not an axiom:

7: quantities and linear resources

Every binder in Wiz carries a quantity, which says how often the body may use the variable at run time:

| quantity | means | for | |---|---|---| | 0 | never: erased | types, proofs, indices like Vec's length | | 1 | exactly once: linear | resources: a file handle, a channel end, the world | | ω | any number of times | explicit binders: the default; an implicit binder defaults to 0 (erased) |

Quantities 0 and 1 on binders.

In [19]:
def id {0 A : Type} (1 x : A) : A := x
def dup {0 A : Type} (x : A) : A × A := (x, x)

id uses x once and A never (only in types), so both quantities are right. dup uses x twice, which is fine at the default ω. Written (1 x : A), the checker would say variable x declared with quantity 1 but used ω. Quantities are checked by the kernel itself, and erasure follows them: an argument at 0 costs nothing at run time.

Quantity 1 gives you linear types: a value that must be used exactly once, never copied and never dropped. That is the right type for a resource:

A linear resource: Ticket and trip use t exactly once with do1.

In [20]:
import IO

axiom Ticket : Type
axiom Ticket.buy : Nat → IO Ticket
axiom Ticket.ride : (1 t : Ticket) → IO Unit

-- `do1` sequences actions whose later steps use linear values: `t` is used once
def trip (1 t : Ticket) : IO Unit := do1
  IO.println "boarding";
  Ticket.ride t

(axiom declares a type or a function without defining it; a real library would implement them with extern, section 9.) Try to cheat and the checker stops you:

Not run: these are the programs the checker rejects, with the errors the tour shows.

def twice (1 t : Ticket) : IO Unit := do1
  Ticket.ride t;
  Ticket.ride t
-- error: kernel rejected twice: variable t declared with quantity 1 but used ω
def lose (1 t : Ticket) : IO Unit := IO.pure ()
-- error: kernel rejected lose: variable t declared with quantity 1 but used 0

do1 is do over IO.bind's linear form (its continuation is used once, so it may capture t). The plain do uses an unrestricted continuation, so trip written with do is rejected too.

Pairs can have linear components. A pair held linearly is taken apart with let 1, which binds both components at once. A projection p.1 would quietly drop the other component, so the checker refuses it on a linear pair:

A linear pair taken apart with let 1.

In [21]:
def swap {0 A : Type} (1 p : A × Ticket) : (1 t : Ticket) × A :=
  let 1 (a, t) := p;
  (t, a)

IO itself is built this way: IO A is (1 w : World) → A × World, a function that takes the world exactly once and hands back the next one, so effects happen in order and can be neither duplicated nor skipped. #check @IO.bind shows the linear binders:

Not a cell: this is output shown by the tour.

IO.bind : {A : Type} → {B : Type} → (1 x : IO A) → (1 f : A → IO B) → IO B

Linear matching on your own data types is not there yet (a match uses its scrutinee at ω), so linear data is written with pairs, as above, for now. (examples/tour/07-quantities.wiz; stages/09-ffi.md, 9a and 9e; stages/25-concurrency.md for linear channels and session types.)

8: codata

An inductive type is defined by how you build its values, and a coinductive type by what you can observe of them. A stream has a head and a tail, forever:

Copatterns define an infinite stream; Stream.take observes a finite prefix.

In [22]:
coinductive Stream (A : Type) where
  head : A
  tail : Stream A

def Stream.from (n : Nat) : Stream Nat
  | .head => n
  | .tail => Stream.from (n + 1)

def Stream.map {A B : Type} (f : A → B) (s : Stream A) : Stream B
  | .head => f s.head
  | .tail => Stream.map f s.tail

def Stream.take {A : Type} : Nat → Stream A → List A
  | .zero, _ => .nil
  | .succ n, s => .cons s.head (Stream.take n s.tail)

def squares : Stream Nat := Stream.map (fun n => n * n) (Stream.from 0)
#eval Stream.take 6 squares                -- .cons 0 (.cons 1 (.cons 4 (.cons 9 (.cons 16 (.cons 25 .nil)))))
#eval squares.tail.tail.tail.head          -- 9
.cons 0 (.cons 1 (.cons 4 (.cons 9 (.cons 16 (.cons 25 .nil)))))
9

The definitions use copatterns: instead of matching on an argument, they say what each observation (.head, .tail) of the result is. An infinite stream is fine as long as every observation answers in finitely many steps (it is productive). The checker makes sure each .tail is a call of the function being defined, guarded by the observation. A definition that would spin forever is rejected:

Not run: this definition is rejected for guardedness, as the tour explains.

def stuck (n : Nat) : Stream Nat
  | .head => n
  | .tail => (stuck n).tail
-- error: the observation .tail must be a corecursive call of stuck (guardedness)

(examples/tour/08-codata.wiz; examples/streams.wiz, examples/sized.wiz for sized types, stages/04-data.md.)

10: hardware

lib/Hdl/Core.wiz is a hardware description library: circuits are Wiz values, simulated by evaluation and turned into Verilog.

A circuit written against any signal representation r; simulate it at values and at a netlist.

In [23]:
import Hdl.Core

def B4 : HwTy := HwTy.bits 4

-- Combinational logic is a function over any representation `r` of signals: run it on
-- values to simulate it, or on wires to get a netlist.
def addThree {r : HwTy → Type} [Hw r] (x : r B4) : r B4 := Hw.add x (Hw.lit 4 3)

-- A circuit is a state type, an initial state and a step: (state, input) ↦ (next, output).
-- This one sums its inputs (mod 16) and outputs the sum so far.
def acc : Circuit B4 B4 :=
  Circuit.mk B4 (BitVec.ofNat 4 0) (fun s x => Hw.pair (Hw.add s x) s)

-- circuits compose: `acc` after `addThree`
def pipeline : Circuit B4 B4 := Circuit.seq (Circuit.comb addThree) acc

#eval Circuit.runPacked pipeline [1, 2, 3, 4]          -- .cons 0 (.cons 4 (.cons 9 (.cons 15 .nil)))
#eval Circuit.simNet Bool.true pipeline [1, 2, 3, 4]   -- the same, from the netlist
def verilog : String := Verilog.emit (Circuit.netlist "pipeline" pipeline)
.cons 0 (.cons 4 (.cons 9 (.cons 15 .nil)))
.cons 0 (.cons 4 (.cons 9 (.cons 15 .nil)))

Hw r is a type class whose instances are representations of signals. At values, Hw.add adds bit vectors. At wires, it adds a node to a netlist. A circuit written once against [Hw r] can be simulated, compiled to a netlist (with shared subterms detected), and printed as Verilog. verilog above is:

Not a cell: this is the Verilog that Verilog.emit prints for the circuit.

module pipeline(input clk, input [3:0] x, output [3:0] y);
  reg [3:0] r_1; initial r_1 = 4'd0;
  wire [3:0] n4 = x + 4'd3;
  wire [3:0] n5 = r_1 + n4;
  always @(posedge clk) r_1 <= n5;
  assign y = r_1;
endmodule

The library also has bundles of named signals (deriving Bundle), reset and enable, test benches, waveforms (VCD) and pin constraints, and the combinators come with lemmas (Circuit.run_seq: running seq a b is running b on the outputs of a). A UART for a Lattice iCEstick FPGA board is written in it. (examples/tour/10-hdl.wiz; examples/hdl.wiz, examples/hdl-compose.wiz; libraries.md, H14.)

11: packages

A program bigger than one file is a grail package: a directory with a grail.wiz, which is itself Wiz:

A grail.wiz package description; grail build is what reads it.

In [24]:
import Grail
def package : Package := Package.new "hello"
  |> Package.lib "greet" "src"           -- the modules under src/: `import Greet` is src/Greet.wiz
  |> Package.exe "app" "App.wiz"         -- compile main to .grail/bin/app
  |> Package.tests "tests" "tests"       -- each tests/*.wiz against its .expected

grail build builds everything (in parallel, and only what changed since last time), grail run app builds and runs a program, and grail test runs the tests: a test is a .wiz file whose messages (or, with -- test: run on its first line, whose output) must match the .expected file beside it. grail test --update writes the .expected files. The tour's own examples are tests of exactly this kind. A wiz-toolchain file next to grail.wiz pins the toolchain, and Package.dep adds a package from a git repository. install.md walks through a first package; stages/23-grail.md has the rest.

It writes a library, an executable and a golden test; grail run hello prints hello from hello, and the test checks the same line. An existing non-empty directory is refused, so new never overwrites work, and the name must start with a letter. (stages/23-grail.md, 23o.)

Modules are files: import A.B reads A/B.wiz from a module root (the standard library lib/, a package's lib directories, -I DIR). Wiz has no namespaces yet, so one name can be declared only once among everything a file imports. Mark helpers private to keep them out of other modules.

12: taint analysis with scry

scry is a program analyser whose library is Wiz: lib/Scry/* has the three-address IR (Scry.Wil), the CFG and reaching definitions (Scry.Analysis), and taint analysis as Datalog (Scry.Taint). A source call's result is attacker-controlled, a sanitiser cleans it, and a sink must not receive a tainted value:

A taint spec, a direct flow and a sanitised one.

In [25]:
import Scry.Taint
import Scry.TaintExamples

def spec : Scry.TaintSpec :=
  Scry.parseTaintSpec "source getenv\nsanitise sanitize\nsink system 0"

#eval Scry.alertsInFunc Scry.directFn spec      -- .cons (4, 0) .nil
#eval Scry.alertsInFunc Scry.sanitisedFn spec   -- .nil
.cons (4, 0) .nil
.nil

The first function copies and adds getenv's result before passing it to system, so the analysis reports the sink and the argument; the second passes it through sanitize, which kills the flow. A finding also carries its source → sink path (Scry.findings). (examples/tour/12-scry.wiz; libraries.md, "Scry".)
