## 8. Supply chain: SBOM, provenance and attestation

The release now carries a CycloneDX 1.6 SBOM for each tarball and an in-toto Statement
v1 whose predicate is the SLSA provenance v1 shape. That provenance is a **claim about
the build inputs and output digests**, not a hosted SLSA build; no SLSA level is
claimed (`wiz:slsaLevelClaimed` is null). A TPM quote and a signed build manifest are
E1 work, and E2 (SEV-SNP) is design only. Do not describe the SHA-256 files, Cachix
signatures or a GitHub release as build attestation.

- [ ] `provenance.intoto.json` names the release workflow and ref as `runDetails.builder.id`,
      the git commit and source tree, the Lean toolchain hash, the locked Nix inputs,
      the five bundled C inputs and the workflow's actions/runner. Its `subject` digests
      match every artifact (both tarballs, both SBOMs, the source manifest).
- [ ] The release notes say in one sentence that this is SLSA-style provenance without
      a hosted level, and that an unsigned provenance is a claim. Do not print "SLSA L2"
      or "SLSA L3".
- [ ] `release-manifest.json`'s `supplyChain` object is filled from the generated files;
      `signed` is false unless the run had `WIZ_ATTEST_KEY`, in which case the DSSE
      envelope and detached signature are assets and the key fingerprint is recorded.
- [ ] With a signing key, verify the statement (`wiz-attest`/`wiz-verify` or the checks
      in `scripts/test_release_sbom.py`) before publishing. Without one, do not describe
      the provenance as signed.
- [ ] Record the negative attestation statement in the release notes and in
      `release-manifest.json` (`"attestation": {"kind": "none", …}`) for TPM/E2
      attestation: checksums, an SBOM and provenance detect corruption and inventory the
      build; they do not prove the builder was honest. If E1's TPM quote is attached
      before the tag, fill the `attestation` object and verify it instead of keeping the
      negative statement.
- [ ] Do not claim reproducible binaries across compilers, or "the build is attested".
      The binary tarball is not yet deterministic; the source tarball is.

This section is deliberately last. The release-notes packet does **not** create a tag,
push, open a PR or publish anything.

      CHANGELOG section, the README install line, and the final Status/release notes.

- [ ] A maintainer creates an annotated tag on that commit and pushes only the tag:

- [ ] `release.yml` runs for the tag: the exercise tree, the tarball build and tests,

- [ ] After the tag, run the online smoke test and the clean-machine install, then open
