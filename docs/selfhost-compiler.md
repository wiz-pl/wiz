# The self-hosted compiler

Wiz's kernel, frontend and compiler are also written in Wiz, under `selfhost/`. This page
says what that means concretely: the files, the bootstrap, the fixpoint, and exactly what
"parity" with the Lean-hosted toolchain does and does not claim. The stage-by-stage
record is [stages 12–21](stages/12-towards-selfhosting.md) and
[stage 30](stages/30-selfhost-typeclasses.md); the short version is
[stage 21](stages/21-bootstrap.md).

## The sources

| file | what it is |
|---|---|
| `selfhost/Lex.wiz`, `Parse.wiz` | the lexer and parser for the Wiz grammar |
| `selfhost/Frontend.wiz` | the scope checker and bidirectional elaborator: syntax to the kernel's terms (`docs/stages/14-selfhost-kernel.md`, `17-selfhost-elaboration.md`) |
| `selfhost/Kernel.wiz` | the kernel: terms, definitions, conversion, typing (`docs/stages/14-selfhost-kernel.md`) |
| `selfhost/Check.wiz` | the checking entry points the driver and the tests use |
| `selfhost/Backend.wiz` | erasure to the backend's `ETm` and C generation (`docs/stages/21-bootstrap.md`, 21a–b) |
| `selfhost/rt.c` | the C runtime: tagged words, objects, the collector, native operations |
| `selfhost/Cli.wiz`, `Main.wiz` | the driver (`check`, `build`, `run`, `eval`, `version`) and its entry point |
| `selfhost/CGlue.wiz`, `CParse.wiz`, `Cof.wiz` | C header/FFI support for the self-hosted path |
| `selfhost/Tables.wiz` | the parser's grammar tables, generated (below) |

`selfhost/Tables.wiz` is generated by `lake build genSelfhostTables`
(`scripts/GenSelfhostTables.lean`); it is the parser's grammar as Wiz data, one
`catN` per category plus `cats` and `tokens`. Its format is the **bootstrap ABI**
(`Cat`, `Leading`, `Trailing`, `PD.*` of `selfhost/Parse.wiz`): a seed parses the file
with its own tables, so the constructors may not change without a seed bump
(`selfhost/Tables.wiz`, first lines; `Wiz/Selfhost.lean`). It is generated, never
edited.

The driver is a real command line, not a generated `main`: `wiz-selfhost check FILE`,
`build FILE -o OUT`, `run FILE [ARG…]`, `version` and `help`, with `-I DIR`,
`--cache`, `--no-cache`, `--cache-verify`, `--target c`, `-v`, `--types`, the C
toolchain flags and the backend flags (`selfhost/Cli.wiz`). Its diagnostics are one line
per error (`file:line:col: severity: message [code]`), using the Lean frontend's error
code where the message names the same mistake (`selfhost/Cli.wiz`).

`run`/`eval` compile with the C toolchain and then run the program with its own words.
`--cc PATH` and `--llc PATH` are **one executable each**, not a command line (use a
wrapper script to add arguments), `--rt DIR` is the directory holding `rt.c`, and
`--cflags`/`--ldflags` are whitespace-separated word lists, as the Lean-hosted `wiz`
reads them. `system(3)` takes a shell string, so the driver POSIX-quotes every
interpolated component — the compiler path, the runtime directory, each flag, an
input/output path, and every program argument — and a path or argument with a space,
`;`, `$`, a quote or a newline stays exactly one word instead of starting a second
command. The program's wait status is decoded (`WIFEXITED`/`WIFSIGNALED`): a program
killed by a signal is a failure, `error: the program was killed by signal N` and exit 1
(the shell's `128 + N`), never exit 0.

## The bootstrap and the fixpoint

Stage 1 is the self-hosted compiler **built by the Lean toolchain** (`Wiz/Selfhost.lean`
assembles the checked-in sources and two build identity values, then `wiz build`
compiles them). That stage-1 binary compiles the whole self-hosted toolchain to C. Each
later stage compiles the previous stage's C with `selfhost/rt.c` and the collector, and
that program compiles the toolchain again (`scripts/fixpoint.sh`).

The check is byte equality: every stage's C must be identical to stage 1's. The default
is three stages — stage 1 = stage 2 shows that the C the Lean-built compiler emits is
reproduced by the compiler that C builds; stage 2 = stage 3 shows that reproduction is a
fixed point, not one coincident round (`scripts/fixpoint.sh`). `--rc` makes every stage
a reference-counting compiler instead of a garbage-collected one (stage 21g–21k), and
`--compare-only` re-checks kept artifacts.

`scripts/fixpoint.sh` needs the toolchain environment (`nix develop`) and about 6 GiB;
the CI job declares that and runs nightly on the heavy runner
(`.github/workflows/fixpoint.yml`), with a weekly `fixpoint` job on `ubuntu-latest` as
the fallback (`.github/workflows/ci.yml`). It is not part of the pull-request suite.

The bootstrap is why the numbers in stage 21 matter: the self-hosted compiler is a few
thousand lines of Wiz that produce tens of thousands of lines of C, and stage 2 runs
much slower than stage 1 (`docs/stages/21-bootstrap.md`, 21d, records both and the
optimisations that followed: string ropes, multi-argument closures, a chain
representation for constructor payloads, reference counting).

## What "parity" means here

Parity is **measured agreement on named observable surfaces**, not a proof:

* **The fixpoint** compares the generated C byte for byte across stages
  (`scripts/fixpoint.sh`).
* **Library parity** (`=selfhost-libdiff`) runs both frontends over every `*.wiz` under
  `lib/` and `scry/` and compares acceptance, the first error's code, its span (file,
  line, column), its whitespace-normalised message, and the number of declarations
  produced for that file. It reports the first divergence, grouped by the construct the
  self-hosted frontend lacks (`by`, `syntax`, `namespace`, …). **It never fails because
  of a gap: it measures** (`Tests/Groups/SelfhostLibDiff.lean`).
* **CLI parity** (`=selfhost-cli-diff`) runs both toolchains over the same input tree in
  a fresh directory and compares the exit code, standard output, standard error, cache
  entries and artifacts — the things a user sees (`Tests/Groups/SelfhostCliDiff.lean`).
* **The selfhost group** checks the driver's own promises (`Tests/Groups/SelfhostCli.lean`).

A pass therefore means: on the cases and files in those groups, the two toolchains
agree. It does not mean the self-hosted toolchain accepts every program the Lean one
does, or that where both accept, the results are semantically identical.

## What parity does not mean

The gaps are documented, tracked and ordinary:

* **Coverage.** The library sweep's gap list is the live measure; the documented
  construction gaps include type classes (a first milestone: default instances,
  `binop` and `outParam` are missing — `docs/stages/30-selfhost-typeclasses.md`), the
  full `Tac`/`Expr` layer the simplifier needs (`docs/stages/06-macros/simp.md`), the
  FFI and library surface (`selfhost/rt.c` has its own FFI and not `lib/Sys` —
  `docs/stages/09-ffi.md`), and privacy beyond names: a type with private parts is
  opaque in the Lean frontend, while the self-hosted one only makes the private names
  private, for the declarations in its slice (`docs/stages/21-bootstrap.md`, 21n;
  `docs/stages/13-language.md`'s table row).
* **A rejected file is not a bug in the same way.** The library sweep counts the files
  whose verdicts differ separately from the files both reject, so the gap list stays
  actionable (`Tests/Groups/SelfhostLibDiff.lean`).
* **The backend is C.** `--target c` is the backend the host names; LLVM and Wasm are
  future work (`selfhost/Cli.wiz`). The self-hosted runtime's `Nat` is 63 bits, so the
  `[S]` column of the [semantics matrix](semantics-matrix.md) is limited to cells that
  fit — a documented bootstrap limitation, not a semantic difference.
* **Diagnostics are approximated.** The driver turns the frontend's `@N text` into a
  compiler-style line and uses the Lean error code where the message maps; it does not
  reproduce every message (`selfhost/Cli.wiz`).
* **Performance is not parity.** Stage 2 is much slower than stage 1, and the
  optimisations in stage 21d are recorded as measurements, not as a guarantee
  (`docs/stages/21-bootstrap.md`).
* **The embedded Prelude can drift.** The self-hosted frontend carries its own Prelude
  text while `lib/Prelude.wiz` is the library's; the duplication is a known drift risk
  (`docs/notes/dogfood-new-features.md`, W7).

So "self-hosted" means the toolchain can check and compile itself, and that this is
checked on every relevant build; it does not mean the two frontends are interchangeable
yet. The list above is the honest boundary, and the sweeps that produce it are the way
to move it.

## Working on it

```sh
nix develop                       # the toolchain environment the scripts expect
scripts/fixpoint.sh               # three stages; --rc for reference counting
lake test -- '=selfhost'          # the selfhost group
lake test -- '=selfhost-cli-diff' # both CLI frontends on the same inputs
lake test -- '=selfhost-libdiff'  # the library sweep (writes .lake/libdiff/)
```

`=selfhost-libdiff` also takes `--only FILE`, `--limit N`, `--json` and `--baseline
FILE` for a focused run or a comparison against a recorded baseline
(`Tests/Groups/SelfhostLibDiff.lean`). A toolchain problem is reported as a skip, the
way the selfhost group skips (`Tests/Groups/SelfhostLibDiff.lean`).
