# Standard-library benchmarks

`stdlib-bench.wiz` measures the standard library's hot data structures; `../scripts/stdlib-bench.py`
drives it, takes repeated samples and writes JSON.  Both are deterministic: a mode does the
same work at the same size on every machine, and prints a checksum of that work (so a
compiler or runtime change cannot delete it as dead code).

```sh
wiz build bench/stdlib-bench.wiz -o bench/.build/stdlib-bench
scripts/stdlib-bench.py --reps 7 --json /tmp/stdlib.json
```

The script builds the program itself (using `.lake/build/bin/wiz` when it exists) and
runs each mode in its own process.  Samples are wall-clock nanoseconds measured with
`time.perf_counter_ns`; the JSON records every sample, the median, variance, standard
deviation and coefficient of variation (`cv`).  Use `--size MODE=N` for an experiment.

## Modes and sizes

| mode | N | work |
|---|---:|---|
| `strmap-insert` | 200000 | build N `Str` keys, insert them all |
| `strmap-find` | 200000 | build the map, 8 passes of N pseudo-random hits |
| `strmap-miss` | 200000 | build the map, 8 passes of N misses (keys prebuilt) |
| `strmap-iterate` | 200000 | visit every entry by its key, 4 passes |
| `array-push` | 2000000 | push N numbers |
| `array-index` | 500000 | build, then 10 passes of N reads and writes |
| `array-map` | 1000000 | build, then map every element into a new array |
| `array-fold` | 1000000 | build, then fold every element |
| `bytes-append` | 2000000 | append a 16-byte chunk N times |
| `bytes-slice` | 2000000 | slice 64 bytes out of an 8 KiB buffer N times |
| `bytes-compare` | 2000000 | compare two equal 4 KiB buffers N times |
| `str-append` | 10000 | append a 100-byte `Str` chunk N times: the `Str.append` builder (1,000,000 bytes at the default) |
| `str-push` | 200000 | push one byte N times: the `Str.push` builder |
| `text-split` | 40000 | split an N-chunk string on `,`, 8 passes |
| `text-replace` | 40000 | replace every `,` with `Z`, 8 passes |
| `text-trim` | 40000 | trim an N-chunk string padded with spaces, 8 passes |
| `text-eq` | 40000 | compare two equal N-chunk strings, 200 times |
| `text-suffix` | 40000 | `endsWith`, `stripSuffix` and `dropEnd`, 3 passes |
| `sort` | 100000 | insert N keys into `U64Map`, read them back sorted 8 times |
| `hash` | 300000 | `NatList.hash` of an 8-number list, 300000 times (a different seed each time) |
| `list-index` | 4000 | 10 passes of N reads of a `List Nat` at a pseudo-random index: the `List` `at`-in-a-loop pattern |
| `egraph` | 3000 | build N e-nodes, union N pseudo-random pairs, then 10·N `find`s (`Scry.EGraph`, whose union-find tables are `U64Array`s) |

`str-append` is the compiled `Str.append` builder: the loop `s := Str.append s piece`
keeps the accumulator unique, so the runtime grows it in place; at the default it
appends 10,000 100-byte chunks (1,000,000 bytes). The old copy-only `wiz_str_append`
and the in-place one produce the same checksum, so an A/B run can use a baseline
built from the same sources with the `a != b && WIZ_RC(a) == 1` branch of
`wiz_str_append` removed. `str-push` is the same builder one byte at a time.

## Comparing two builds

Two runs of the same build differ by several percent when other work shares the machine.
For a change, build the old and new executables and interleave them:

```sh
scripts/stdlib-bench.py --baseline-bin /tmp/old-bench --reps 15
```

This alternates one run of each per sample, changing which build goes first, and
reports the median of the per-pair ratios (with the min and max and every ratio), which
cancels machine drift.  `--baseline FILE` instead compares the medians with an earlier
JSON; `--fail-regression PCT` turns a slowdown into exit status 1, and
`--allow-checksum MODE` permits a deliberate checksum change (a new hash function, say).
`--bin FILE` runs an existing executable without rebuilding it (the usual way to keep
the A side of a comparison).

`stdlib-baseline.json` is a recorded reference run and `stdlib-bench.json` the run after
the changes, with both the samples and the interleaved `ab` ratios.  Absolute times move
with machine load; use `--baseline-bin`, not two separate runs, to decide whether a
change is a regression.  Regenerate the reference after a deliberate change and keep the
old file.

## Self-hosted performance (host vs self-hosted)

`selfhost-bench.py` answers the *performance* half of replacement parity: on the same
files, with the same flags, how much slower and larger is the Wiz-hosted frontend than
the Lean host?  Build both toolchains first (the self-hosted one is generated by
`scripts/GenSelfhost.lean` with its driver and cache):

```sh
heavy --mem 6G bench/selfhost-build.sh
bench/selfhost-bench.py                 # measure, print the table, update the JSON
bench/selfhost-bench.py --check         # fail if self/host is >20% above the record
bench/selfhost-bench.py --check --tolerance 10
bench/selfhost-bench.py --update-baseline
```

The driver is `bench/.build/selfhost`, i.e. its `check FILE` subcommand (the same
`--no-cache` / `--cache DIR` pair as the host's `wiz check`).  Both run from the repo
root; the self-hosted side gets `-I lib` because its loader has no built-in library
root.  Each sample is one process, and wall time is `perf_counter` around it, so process
start-up is included on both sides.  Peak RSS is GNU `time`'s `%M` (the child's
`wait4` rusage), not a sampled `VmHWM`: a short check keeps its true peak.

Two cache states are measured: `cold` (`--no-cache`, every sample re-elaborates) and
`warm` (a fresh `--cache DIR` per tool, warmed once before the samples).  The corpus is
the fixed `CORPUS` list in the script, and every file in the tracked run was accepted by
both tools; a file one side rejects is reported as *unsupported* and left out of the
ratio (a rejection is not a check).  `lib/Prelude.wiz` is interesting because the
self-hosted frontend embeds its own prelude: a file importing `Prelude` does not
elaborate the same bytes on the two sides, which is a parity property, not a flag.

A representation difference is not a work difference here: the self-hosted runtime's
`Nat` is a 63-bit word and the host's is unbounded, but no corpus file evaluates a
`Nat` at or above 2^63, so both sides do the same arithmetic. A file that crossed the
boundary would be a correctness difference first, and would not belong in this corpus.

The gate is relative: `selfhost / host` per file and for the corpus total (the sum of
per-file medians; peak RSS is the maximum, since the files run one after another).
`selfhost-bench.json` records the samples and `baseline_ratios`, which `--check`
multiplies by `1 + tolerance`; absolute seconds differ between machines, the ratio does
not.  `--check` exits 1 when a file or the total is worse than that, and also when a
file the baseline checked is rejected now.  Update `baseline_ratios` only for a
deliberate change (a new corpus entry, a changed prelude), not to make a run green.

## Memory

`../scripts/mem-bench.py` measures peak RSS (not time) of a fixed corpus: cold checks of
`lib/`, the largest example, a `wiz build`, and the self-hosted checker. It records
`mem-baseline.json`, gates a run at +25 % relative and at a per-invocation hard cap, and
has a `--self-test` for the thresholds. See docs/building.md, "Memory budget".
